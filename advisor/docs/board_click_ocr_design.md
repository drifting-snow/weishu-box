# 棋盘阵容识别设计：点击识别，而非 OCR 2D 小人

状态：设计稿（2026-11-12，基于真实 2560×1440 准备界面 `concrete_ui.png` 实测）
作者协作说明：本文件是给棋盘 OCR 实现者的方案，不改动 `vision/board_strip_ocr.py` 等在途代码。

---

## 0. 一条不可违背的红线

模拟点击**只用于"识别"**：点一个已拥有的单位 → 弹出只读详情面板 → OCR 面板上的干员名 → 关闭面板。
**绝不代替玩家操作游戏**：不发购买、刷新、冻结、升本、部署、拖拽等任何会改变局面的点击。
现有产品定位是只读参谋，所有点击都必须可证明"无副作用"。

---

## 1. 为什么不能直接 OCR 棋盘上的 2D 小人（实测结论）

对 `concrete_ui.png` 的放大核对：

- 备战区（冻结按钮左侧的水平浅色矩形格）和主棋盘（等距地砖）上的已拥有单位，**全部是无名字的 Q 版立绘**，头顶只有 `I`/`II` 这类精英/本数标记，**没有任何干员名字文字**。
- 因此"对一条 strip 做 OCR 再 snap 干员名"的假设（`board_strip_ocr.py` 当前路线）在真实画面上**没有文字可 OCR**，只能读到 UI 词（冻结/刷新/剩余可放置角色），无法得到阵容。
- 唯一稳定带名字的文本，是**点击单位后弹出的详情面板**。这与敌人面板（点放大镜 → OCR 名字）是同一套已验证思路。

正确链路：**检测哪些格站了人（占位，不认人）→ 逐格点击 → OCR 详情面板名字 → 聚合成 `List[BoardUnit]`**。

---

## 2. 目标输出与复用边界

- 产物形状必须等于 `advisor/board_io.py` 已接受的 `List[BoardUnit]`（`name/count/elite/tier/bonds`），同名副本走 board_io 的合并逻辑，bonds/tier 由数据集补全。
- 名字吸附复用 `vision/match_text.py` 的**保守模式**（`conservative=True`，与敌人面板同门槛），字典用 141 干员名，避免近名误吸。
- 不要重写 `shop_band_ocr.py`；OCR 引擎复用 `BandOCREngine`，截图复用外壳 `capture_live.grab_primary`。
- 引擎侧已就绪：`GameState.board` 一填充，阵容罗盘 `compass.py`、构筑路线 `roadmap.py`、羁绊/三合一/里程碑评分全部自动生效。本设计只负责把 board 填对。

## 3. 两个区域的几何（实测 fraction，需用校准脚本复核）

画面 2560×1440，坐标建议全部用 fraction 存，运行时按真实分辨率换算（参照 `vision/roi.py` 思路）。

### 3.1 备战区（水平条，优先级最高）
- 实测大致范围：`x≈0.62–0.86 W`，`y≈0.57–0.74 H`，是一排等宽浅色圆角矩形格。
- **必须 mask 掉右侧控件区**：冻结（S）/刷新（D）按钮在 `x>~0.86W`，高饱和，原型里正是它们造成了占位误报。占位检测的右边界要卡在冻结按钮左缘以内。
- 格数可能随调度等级变化（待样本确认，见 §7）。先用"固定 N 等分 + 每格打分"，N 做成可配置。

### 3.2 主棋盘（等距地砖）
- 等距网格，相邻格沿两个斜轴等间距排列；部分地砖被地形（箱子、植物、建筑、悬索桥）占据，不可站人，枚举时要跳过。
- 建议用一组 `(i,j) → 像素中心` 的基向量映射，基向量和原点用一次人工校准得到，之后按网格推算，不要每格写死坐标。

### 3.3 占位检测（只回答"有没有人"，不回答"是谁"）
原型 `bench_occupancy_proto.py` 已验证思路可行（正确检出唯一 chibi），但需要更稳的特征与 UI mask：
- 特征：格内**边缘密度**（立绘轮廓 vs 空地砖规则纹理）+ **彩色饱和度占比**（立绘鲜艳、金属格低饱和）+ 可选"脚下圆形底座光圈"检测。
- 判定：相对同条带中位数的倍数阈值（原型用 edge>1.15×median 或 sat>1.25×median），阈值用多帧标定，不要拍常数。
- 输出候选格中心列表，交给点击层；宁可多报（点到空格无面板会被判空），不可漏报。

## 4. 点击层（外壳当前缺失，需要新增 Win32 原语）

外壳现有 `win32_util.py` 只有置顶/分层/热键，**没有任何鼠标 API**。新增一个最小点击模块（建议 `shell/input_click.py`）：

- 推荐 `SendInput`（比 `mouse_event` 现代），一次"左键 down/up"即一次单击；进程已 `SetProcessDpiAwarenessContext(per-monitor v2)`，坐标用物理像素。
- 悬浮窗保持 `WS_EX_TRANSPARENT`（click-through），让点击落到下层游戏窗口，而不是点到自己的面板。
- 只暴露一个 `left_click(x, y)`，且函数内做**硬边界断言**：坐标必须落在棋盘/备战区 ROI 内，否则拒绝执行。不提供拖拽、双击、右键、长按等接口，从 API 面就杜绝越权操作。

### 识别会话状态机（每个候选格）
1. 记录会话前快照：金币/本数（`resource_ocr`）+ 商店带截图 hash，作为"无副作用"基线。
2. `left_click(格中心)` → 等待面板动画 settle（建议 150–300ms，实测调）。
3. 截图，判定详情面板是否出现（面板出现的视觉标志待 §7 样本标定；可先用"屏幕固定 ROI 内出现大字号名字文本"作为判据）。
   - 出现：OCR 名字区 → 保守 snap 到干员字典 → 记录 `BoardUnit`。
   - 未出现（空格/地形）：判空，不产出。
4. 关闭面板：优先按 `ESC`（只读、安全），或点一次棋盘空白；再截图确认已回到棋盘（幂等检查）。
5. 任何一步检测到异常弹窗或画面不符 → 按 ESC 取消、记 `warning`、跳过该格，**不盲点后续**。
6. 会话结束后再算一次金币/本数/hash，与基线比对；任何变化立即报错并标记本次结果不可信（理论上只读点击不会变，这是安全审计）。

护栏：单次会话点击数上限；用户热键可随时中断；默认不自动循环，仅在用户显式触发"识别阵容"时跑一次。

---

## 5. 聚合为 board

- 每个被成功识别的格产出一个名字；备战区 + 主棋盘结果合并，同名累加 `count`（复用 `board_io.parse_board` 的合并与数据集补全）。
- 精英形态：详情面板通常会显示精英/本数差异，若面板有可靠标记再填 `elite`，否则留默认 `False`，不要猜。
- 识别置信度低（保守 snap 返回歧义/unknown）的单位放进 `warnings`，不静默塞入，交给用户人工确认。
- 产出与 `--board` 手填 JSON 完全同构，使手动/自动两条输入可互换。

---

## 6. 推荐落地顺序（小步可验证）

1. 先只做**备战区**：固定 ROI + 占位打分 + 单格点击 + 面板 OCR，跑通"点一个人出一个名字"的最小闭环（主棋盘等距枚举更复杂，后置）。
2. 用 §7 样本标定详情面板名字 ROI 与"面板出现/关闭"判据。
3. 加 ESC 关闭与幂等检查、安全基线 hash 审计。
4. 再做主棋盘等距网格枚举与地形跳过。
5. 接进 CLI/外壳：识别结果走 `board_io` 入口进 `GameState.board`，与现有 `--board` 合流。
6. 每个纯逻辑环节（占位打分、格坐标映射、面板出现判定、名字聚合）都拆成无 OCR/无点击的纯函数配单测，点击与 OCR 用接口注入，沿用本仓"纯逻辑可离线测、IO 可替换"的约定。

## 8. 实测标定更新（2026-11-12 晚，样本 `点击干员.png`/click_operator.png，2560×1440）

玩家已提供点击单位后的真实详情面板，下列为读图硬数据，取代此前的推测坐标。

### 8.1 详情面板 = 左侧固定大面板（名字 OCR 极稳）
- 点中一个已拥有单位后，屏幕**左侧滑出固定信息面板**，干员名为左上白色大号字（样本：`拉普兰德`），名字 ROI 实测 fraction 约 **x 0.005–0.175 / y 0.235–0.345**，字号巨大、对比强，OCR 可靠性高。
- 名字下方依次是：黑底白竖条 **Ⅰ 精英标记** + `LV 55`、攻击/防御/法抗/阻挡/费用、蓝色生命条 `1759/1759`，以及特质/技能/特性/天赋页签和攻击范围小窗。
- 即：**名字区位置与是否选中无关、固定在左侧**，可直接定 ROI 做单行 OCR，再用 match_text 保守模式 snap 到 141 干员字典。

### 8.2 玩家提出的「Ⅰ/Ⅱ 标记反推」已验证可行（推荐作为主占位锚点）
- 棋盘上每个已拥有单位头顶都有一个**黑底白竖条的小方块标记**（Ⅰ 一道竖条、Ⅱ 两道），高对比、固定样式，比通用边缘/饱和度占位稳得多，且天然给出单位计数。
- 实测两个同排标记中心约 **(1190,805) 与 (1375,805)**：同高、间距 ~185px（恰为一格宽），可据此恢复等距网格行列。
- **标记 → 单位点击点 = 往右下偏移**，实测 **dx ≈ +32、dy ≈ +122 px**（2560×1440），落点在 chibi 躯干。玩家口述的「右下点一下就是干员」方向正确。
- 安全性：选中后弹出的黄色「出售」按钮在标记的**右上方**，而单位本体在标记**下方**——往右下点击天然避开出售按钮。关闭面板统一走**左上角 ESC**（截图确认 ESC 入口在左上），不要点屏幕内任何按钮。
- 玩家另确认：**没有干员时点击地板完全无反应**，因此「点击后左侧面板是否出现」就是干净的有人/没人判据，无需专门识别空格。

### 8.3 两个已踩中的检测陷阱（实现时规避）
1. **选中态高亮污染**：click_operator.png 是「已选中某单位」状态，全屏叠加橙白斜纹菱形高亮，导致标记的黑白对比被冲淡（右标记中央竖条亮占比实测仅 0.01、边框/内芯都不够黑），且空地砖橙纹饱和度反高于单位本体，使「饱和度占位」在此态失效。→ 标记模板/阈值应在**普通未选中准备态**截图上标定；识别会话逐格点击时也应每读一个单位就 ESC 回到普通态再截下一帧。
2. **粗糙暗密度滑窗会误检 UI**：仅用「暗块密度」的滑窗把左侧 Q 技能面板的暗块误判成标记，还漏掉被高亮干扰的真标记。→ 必须用**规整形状匹配**（亮圆角边框 + 暗内芯 + 中央 1~2 根细竖条的模板/连通域长宽比），并把检测 ROI 限定在棋盘/备战席，排除左侧技能面板、右侧出售/冻结/刷新按钮区。

### 8.4 修订后的识别主流程
1. 在普通准备态截图上用「Ⅰ/Ⅱ 形状模板匹配」检出所有头顶标记，得到标记中心列表（同时恢复网格行列、给出单位总数）。
2. 每个标记中心 + 固定右下偏移 (dx,dy) 算出该单位点击点；偏移按分辨率缩放（用 fraction 或标定常数）。
3. 逐格：点击 → 等左侧面板出现 → OCR 固定名字 ROI → 保守 snap → ESC 关闭并确认回到普通态 → 再处理下一格（避免选中态高亮污染后续检测）。
4. 点地板无面板即判空，跳过；聚合仍走 board_io，输出与 `--board` 同构。

## 8.5 检测算法已在真实四帧上验证可行（2026-11-12 晚，纯 numpy 无新依赖）

用玩家提供的 `普通未选中态.png / 普通未选中-二星.png / 选中-二星.png / 选中-备战席.png`（均 2560×1440）做了完整算法验证，诊断脚本 `_diag/vision/badge_ncc.py`、`badge_verify.py`、`badge_profile.py`。**结论：普通未选中态下检测达 100% precision + recall。**

### 六档（Ⅰ–Ⅵ）：Ⅰ–Ⅲ 已标定，Ⅳ–Ⅵ 已采样但检测器待重构（2026-11-12）
玩家明确：头顶标记精英等级是 **Ⅰ/Ⅱ/Ⅲ/Ⅳ/Ⅴ/Ⅵ 六档**。Ⅰ–Ⅲ 为暗底+亮竖条（罗马 Ⅰ/Ⅱ/Ⅲ 竖条字形）；**拿到高本帧后发现 Ⅳ–Ⅵ 是亮彩底（Ⅳ青/Ⅴ黄/Ⅵ橙）+深色罗马数字（Ⅴ含斜线、Ⅵ=Ⅴ+Ⅰ），明暗极性与字形都变了**。早期“单模板即可定位全部档位”的推断只对了一半：NCC 因减均值对整体亮度不敏感，仍能在彩标位置起中等峰，但旧 `darkening≥25` 门控要求“标记比背景暗”，把亮底彩标系统性误杀（实证见 §8.6）。**当前检测器在高本帧只稳定召回暗底 Ⅰ/Ⅲ；Ⅳ–Ⅵ 召回需门控重构。精英档位最终以点开面板读到的 Ⅰ–Ⅵ 文案为准**，标记仅用于定位与计数。

### 验证通过的三段管线（实现照此）
1. **NCC 模板匹配**：从普通态确认标记 `TPL_BOX=(834,354,910,420)`（76×66）提灰度模板，FFT 做全图归一化互相关。关键：局部归一化分母必须加**绝对方差下限 `VAR_FLOOR=15²`**，否则选中态大片平坦水面/橙纹（局部方差趋零）会把分数撑爆到 1e4（真 NCC 必在 [-1,1]）。NCC 原始峰极多（一帧 ~500 个超阈像素），仅作候选来源。
2. **数据驱动形状门控（决定性一步）**：对每个 NMS 后候选算两个特征——`darkening`=标记块均值相对外围地砖环的变暗量；`barVsInner`=中央最亮列相对暗内芯的亮度差。在 7 真 6 假样本上剖面得到**无重叠鸿沟**：
   - 真标记 `darkening` 全部 **≥26.7**（实测 26.7–54.0），假阳性全部 **≤23.1**（-14.5～23.1）；取门限 **darkening≥25 且 barVsInner≥20**。
   - 这一步单独挡掉全部假阳性：空地砖（darken -14.5，含拿到 1.05 NCC 高分的 (1957,832) 冻结按钮雪花图标）、木箱（11.1）、深绿装置（17.6/23.1 但 barVsInner 仅 4.6）、底部商店卡黑图标（7.7/13.1）。
3. **行列网格聚类**：真标记严格成等距点阵（高台 y≈387 / 底座 y≈540 / 地面 y≈644，x 间距 ~145–155px），散点剔除（`ROW_TOL=34`、`GRID_HALF=78`）。

## 8.6 高本帧实证：Ⅳ–Ⅵ 亮极性标记击穿旧门控（2026-11-12 晚，诊断脚本 `_diag/vision/`）

样本：`有高本干员.png`（普通态，规程等级13、回合9，2560×1440，含 Ⅳ青×1/Ⅴ黄×1/Ⅵ橙×2 + 多个 Ⅲ绿/Ⅰ黑）、`选中高本干员.png`（选中态，不作检测帧）。跑现有 `detect_badges` 仅得 **6 个且全判 tier=1**，肉眼可见十几个标记 → 严重漏检。逐层归因：

1. **明暗极性反转**：Ⅰ–Ⅲ 是暗底亮条，Ⅳ–Ⅵ 是亮彩底+深色罗马字。旧 `darkening`（标记块均值 vs 外围地砖环，要求标记更暗 ≥25）在亮底标记上反转到负值/低值，被门控系统性杀掉。
2. **字形变了，数竖条原理失效**：Ⅳ/Ⅴ/Ⅵ 是罗马数字字形（Ⅴ 是两条斜线），不是 Ⅰ/Ⅱ/Ⅲ 那种等宽竖条；`_shape_gate` 的列分组计数对高档位不适用，判级必须另找路子（颜色或点击后面板 OCR）。
3. **颜色分割 go/no-go 实测（HSV，纯 numpy）**：
   - 冷色可分：青色相 170–200° 掩码极干净，Ⅳ 标记被精确抠出、沙漠零污染；绿色 140–170° 同理（掩码像素 青 12878 / 绿 4266）。
   - 暖色判死刑：本关沙漠地砖本身就是橙色相，橙掩码 51.8 万像素淹没一切；暖色饱和度主峰在 S≈0.5（29.7 万），而 Ⅵ 标记 S≈0.5–0.63、Ⅴ 仅 0.16，**色相与饱和度都与背景重叠，V/VI 无法靠颜色在沙漠关分割**。
4. **反相模板失败**：把暗底模板 `255-x` 反相后跑 NCC，峰全落在空白地块/木板/箱子/按钮（18 峰无一压中真标记）——简单反相破坏了圆角外框的正确边缘关系。NORMAL 模板反而能框住橙 Ⅵ/黄 Ⅴ，证明 **NCC 跟的是外框结构、对极性不敏感，问题只在门控不在模板**。
5. **NCC 塌缩 bug（已修）**：冻结/刷新按钮等近平坦区（std≈1.7）把归一化相关系数撑出数学范围，实测 2.21、3.78（合成探针稳定复现到 3.4–3.6、最低 −5.86），`VAR_FLOOR` 未完全压住。已在候选阶段硬剔除 `|score|>1`（真 NCC 必 ∈[−1,1]），并加两个回归测试。注：该修复是数学正确性加固，非 Ⅳ–Ⅵ 召回的决定因素（旧 shape_gate 本也会拦负 darkening 的塌缩点）。
6. **旧 darkening 鸿沟在拥挤高本帧消失**：8.5 的 26.7 vs 23.1 干净间隔只在稀疏帧成立；高本帧真标记 dark_signed 跨度 −12～+58，假阳性（箱子/地块/木板）落在 −12～+13，**严重重叠**；饱和度同样分不开（假阳性 0.5–0.83，真标记 0.1–0.7）。单靠局部明暗/颜色门控原理上不够。

### 重构路线（待多帧验证，勿在单张沙漠图硬调）
- **定位（召回）**：保留单模板 NCC（对外框、跨极性有效），门控从“darkening 单向变暗”改为**极性自适应**——取 `|标记块均值 − 外围环均值|` 的绝对对比，配合“内部存在高对比边缘（亮条或深色罗马字）”，而非规定谁亮谁暗。
- **真假抑制（关键）**：高本帧假阳性多为等距箱格/地砖/红框，必须上**网格晶格约束**——标记落在单位格点等距点阵上，用 RANSAC/霍夫估行列步长，只保留晶格内候选、剔除散点；ROI 继续硬排除右侧敌人红框区与冻结/刷新按钮。
- **判级**：冷色（Ⅲ绿/Ⅳ青）可直接由色相约分档位；暖色 Ⅴ/Ⅵ 在沙漠关颜色不可靠，**高档位等级一律以点击后面板 OCR 的 Ⅰ–Ⅵ 文案为准**，标记只负责定位+计数，不强行自动判级。
- **回归保护**：现有 9 个合成测试锁 Ⅰ–Ⅲ 暗底路径不被破坏；新门控需在稀疏旧帧（保 precision/recall）与高本帧（提 Ⅳ–Ⅵ 召回）双轨验证，阈值禁止单图过拟合。
